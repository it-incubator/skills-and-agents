# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

The it-incubator team's **shared library of agent skills** for AI coding tools (Claude Code, Codex,
Cursor) — plus the mechanism that distributes them to developers' machines.

There is **no application code**: no build, no lint, no tests, no CI, no `package.json`, no
Dockerfile, no ArgoCD Application, no domain. The whole repository is markdown skill definitions
(one `SKILL.md` per skill), a handful of TypeScript **templates that are copied into other projects
and never compiled here**, and the sync skill. As of this writing: 16 skill definitions, ~24 `.md`
files, 8 `.ts` templates.

When asked to "change the project" here, it essentially always means **editing a `SKILL.md`**.

This is where the `in-*` skills a developer sees in their slash menu come from. If a skill behaves
wrongly in some other repo, the fix belongs here, not there.

## Layout

```
skills/<skill-name>/SKILL.md          source of truth — one directory per skill
skills/<skill-name>/references/*.md   optional deep-reference docs the skill loads on demand
skills/<skill-name>/templates/*       optional files the skill copies into the target project
.claude/skills/in-sync-skills/        bootstrap copy of the sync skill (the one you edit)
.codex/skills/in-sync-skills/         mirror, generated by step 9 of the sync skill
.cursor/skills/in-sync-skills/        mirror, generated by step 9 of the sync skill
agents/                               does not exist yet; /in-sync-skills picks it up if added
```

- `skills/<skill-name>/SKILL.md` — the **source of truth** for every skill.
- `.claude/skills/`, `.codex/skills/`, `.cursor/skills/` — **bootstrap copies** containing only
  `in-sync-skills`, so a freshly cloned developer can invoke the sync skill regardless of which tool
  they opened the repo in.
- `in-sync-skills` is deliberately the **one skill with no `skills/` copy** — it only works when run
  from inside this repo (its step 1 aborts otherwise), so a global copy would be dead weight, and
  leaving it out of `skills/` keeps step 6 from ever syncing it into anyone's global config. It
  lives only in the three bootstrap dirs above. Edit the `.claude/skills/in-sync-skills/` copy;
  step 9 of the skill mirrors it into the `.codex` and `.cursor` copies. Commit all three.
- **`in-sync-skills` must NEVER live in a global config** (`~/.claude/skills/`, `~/.codex/skills/`,
  `~/.cursor/skills/`) or in any project's `.<tool>/skills/`. It is a repo-only skill, invoked from
  inside this repo via `/in-sync-skills`. If a stale global copy exists (e.g. installed manually by
  an older workflow), delete it — `rm -rf ~/.<tool>/skills/in-sync-skills`. It is **not** a
  team-library skill that got removed, so orphan detection must not offer to re-sync it; it simply
  should not be there.
- Only `in-nestjs-e2e` currently uses the `references/` + `templates/` sub-layout. The `.ts` files
  under `templates/` are **payload, not source** — they are `rsync`ed verbatim into a target project
  and are deliberately not type-checked here (there is no `tsconfig.json`).

## What is in the library

`ls skills/` is the authority; this grouping is for orientation.

| Family | Skills | What they do |
| --- | --- | --- |
| **Architecture / docs generation** (`in-arch-*`, `in-docs-*`) | `in-arch-c4-diagrams` (C4 L1–3), `in-arch-c4-code` (L4), `in-arch-deployment-diagram`, `in-arch-dynamic-diagrams`, `in-arch-er-diagram`, `in-arch-use-case-diagrams`, `in-arch-sequence-for-usecase`, `in-service-map`, `in-docs-audit`, `in-docs-write` | Read a project's code and emit PlantUML / YAML / markdown into its `docs/`. The biggest family and the one that most often needs a fix. |
| **NestJS code work** | `in-nestjs-e2e`, `in-swagger-fix` | Scaffold or repair code inside a NestJS project. |
| **Meta — managing skills themselves** | `in-add-global-skill`, `in-delete-global-skill`, and the repo-only `in-sync-skills` | Create/remove a *personal* global skill; distribute *team* skills. |
| **Workflow** | `in-commit`, `in-grill-me` | Commit-message generation; plan interrogation. |

The `in-arch-*` / `in-docs-*` family is chained: `in-service-map` produces
`docs/dependencies/service-map.yaml`, which feeds `in-arch-use-case-diagrams` and
`in-arch-c4-diagrams`, and `in-docs-audit` indexes whatever the others wrote. A change to the output
path or filename in one of them silently breaks the next one — grep the whole family before
renaming an output artifact.

Several skills also exist in a **non-prefixed personal form** in some developers' configs
(`c4-diagrams`, `swagger-fix`, `grill-me`, `add-global-skill`). Those are pre-namespace leftovers,
not shipped from here, and must not be re-created under `skills/`.

## Precedence: why names matter here

Skills and agents resolve name collisions in **opposite** directions. Both verified experimentally,
not just read off the docs.

| | Same name in personal and project config | Result |
| --- | --- | --- |
| **Skills** | `~/.claude/skills/X` vs `<project>/.claude/skills/X` | **personal wins** — the project copy never reaches the model's skill list at all |
| **Agents** | `~/.claude/agents/X.md` vs `<project>/.claude/agents/X.md` | **project wins** (`.claude/agents/` is priority 3, `~/.claude/agents/` is 4) |
| **CLAUDE.md** | user + project | neither wins — all files are concatenated; on contradiction the model picks arbitrarily |

Consequences for this repo:

- **The `in-` prefix is not decoration.** A team skill installed globally silently shadows any
  project skill of the same name — the project's version stops existing as far as the model is
  concerned, while the slash menu still lists both. The prefix keeps team skills out of that
  collision.
- **Never claim a bare, likely-used name** (`commit`, `review`, `deploy`, `write-e2e-tests`) for a
  skill that ships from here.
- **Agents added under `agents/` must keep plain names** (`designer`, `developer`, `qa`, `tester`) —
  *not* `in-designer`. Because project agents override personal ones, a project that ships its own
  `designer` is meant to win, and a prefixed name would break that by making both visible at once.
- When a project deliberately specializes a skill (e.g. a starter-kit fork's own e2e skill), the two
  must have **different names** — same-name "overlay" does not work, the project copy is invisible
  rather than merged. The **project-side** skill carries the discriminator in its `description`, and
  the project's own `CLAUDE.md` states which to prefer. Skills shipped from here stay unaware of
  their consumers: a general library that lists every downstream convention grows with each new one
  and pays for it in every session.

## Skill conventions

- All skill names are prefixed `in-` (team-namespace marker), e.g. `in-commit`,
  `in-arch-c4-diagrams`. Architecture-diagram skills use the `in-arch-` prefix.
- **Frontmatter is exactly three lines and uniform across the library**: `---`, `name:`,
  `description:`, `---`. Every `SKILL.md` currently matches this to the line. Keep it that way — no
  extra keys, no blank line inside the block.
- `name` must equal the directory name. Nothing checks this; a mismatch surfaces as a skill that is
  installed but never triggers.
- The `description` must state when to use the skill and include trigger phrases in **both English
  and Russian** — this is the text the agent matches against, so it is the skill's entire discovery
  surface. A skill with a vague description is a skill that never fires.
- Body structure follows the existing skills: `## Purpose`, then numbered `## Steps`; add
  `## Architecture`, `## Locked policies`, or `## Trigger phrases` sections when the skill needs
  them. Bodies run 96–280 lines; `in-grill-me` (10 lines) is the deliberate minimal case.
- Write skill bodies in **English**, including examples and diagram captions.

## Nothing here is validated — plan accordingly

There is no CI, no linter, no schema check, and no test that a `SKILL.md` is well-formed. A broken
frontmatter, a wrong `name:`, or a dangling `references/` path fails **silently and remotely**: the
tool simply stops listing the skill in the developer's menu, and nobody learns about it until
somebody notices the slash command is gone. Before committing a skill change, at minimum re-read
the frontmatter and confirm every path the body tells the agent to read actually exists.

## How a change here reaches developers

Distribution is **pull-based and manual**. Developers run `/in-sync-skills` from inside this repo,
which physically copies (rsync, never symlinks — Windows-safe) each directory under `skills/` (and
`agents/`, if it exists) into `~/.<tool>/skills/` or `<project>/.<tool>/skills/`. Consequences:

- **Merging to `main` changes nothing on anyone's machine.** There is no webhook, no auto-update, no
  version pin. A developer runs on whatever they last synced, which may be months old.
- Sync is **additive at the item level**: it overwrites skills that exist in this repo but never
  deletes a developer's personal (non-`in-`) skills in the destination.
- **A rename is a two-sided operation.** The old directory keeps living in every developer's config
  as an `in-*` **orphan**. `/in-sync-skills` detects orphans, explains them from this repo's git
  history (`--diff-filter=DR`), and offers deletion — which is why a rename should be a *single
  commit with a clear subject line*: that subject is the explanation a developer sees months later.
- Because sync reads the **working tree**, a developer who syncs from a feature branch installs that
  branch's skills. Prefer syncing from `main`.

## Commits

Conventional Commits with the `skills` scope, e.g. `feat(skills): add in-arch-sequence-for-usecase`,
`refactor(skills): rename in-commit-message to in-commit`. Commit subjects double as orphan-deletion
explanations (see above), so make them say what happened to the skill.

Work happens on short-lived `fix/*` branches merged into `main` via PR.
