# Уточнения к архитектуре и Storybook

Этот документ фиксирует решения противоречий между `ARCHITECTURE.md` и `stories.md` и внутри них. Исходные документы пока не меняются. При совместном чтении спорные формулировки следует трактовать согласно уточнениям ниже.

Все семь решений ниже согласованы. Они определяют, как разрешать обнаруженные противоречия при чтении исходных документов, но не означают, что сами документы или код проекта уже приведены к этим правилам.

## 1. Local First относится к slice страницы, а не к одному файлу

Новый код начинается внутри `pages/{page}/`. Компонент страницы отвечает за отображение и связывание частей UI. Query hooks, mutation hooks, query keys и связанная логика могут с самого начала находиться в локальном `model/` этой страницы.

```text
pages/assessment/
├── ui/
│   ├── index.tsx
│   └── components/
└── model/
    ├── queryKeys.ts
    └── useCurrentAssessmentQuery.ts
```

Пример локальных ключей:

```ts
// pages/assessment/model/queryKeys.ts
export const assessmentsKeys = {
  all: ["INTERVIEW", "assessments"] as const,
  current: () => [...assessmentsKeys.all, "current"] as const,
};
```

Пример локального запроса:

```ts
// pages/assessment/model/useCurrentAssessmentQuery.ts
"use client";

import { useQuery } from "@tanstack/react-query";
import { getMainClient } from "@/shared/api/main-api-client";
import { unwrap } from "@/shared/api/utils/unwrap";
import { assessmentsKeys } from "./queryKeys";

export function useCurrentAssessmentQuery() {
  return useQuery({
    queryKey: assessmentsKeys.current(),
    queryFn: () =>
      unwrap(getMainClient().GET("/api/v1/assessments/current")),
  });
}
```

Компонент использует локальную модель:

```tsx
// pages/assessment/ui/index.tsx
"use client";

import { useCurrentAssessmentQuery } from "../model/useCurrentAssessmentQuery";

export default function AssessmentPage() {
  const assessment = useCurrentAssessmentQuery();

  if (assessment.isPending) return <div>Загрузка...</div>;
  if (assessment.isError) return <div>Ошибка загрузки</div>;
  if (assessment.data == null) return <div>Нет текущего assessment</div>;

  return <pre>{JSON.stringify(assessment.data, null, 2)}</pre>;
}
```

Отсюда следуют уточнения исходных правил:

- «Write all code directly on the page first» означает размещение внутри slice страницы, включая `ui/` и `model/`.
- Запрет query hooks в файле страницы касается определения логики запроса внутри UI. Вызывать импортированный hook из компонента страницы разрешено.
- Указания «query hooks и types — в entity/model», «mutation hooks — в feature/model» описывают размещение **после выделения** соответствующих entity и feature.
- Query keys до выделения entity принадлежат локальной модели страницы. При выделении entity ключи переносятся вместе с запросами, без изменения значений ключей.
- Наличие серверного запроса само по себе не требует создания entity. Наличие мутации само по себе не требует создания feature.
- Локальная модель не обязана быть маленькой: выделение hook в `model/` не считается преждевременной декомпозицией на нижние слои.

Когда данные или UI доменного объекта действительно нужны нескольким страницам и выполнены критерии выделения entity, общая часть переносится в `entities/{entity}/model/` и при необходимости `ui/`. Страничная логика остаётся на странице. Другие slices не импортируют локальный `model/` этой страницы.

Мутации остаются в локальном `model/`, пока действие не соответствует критериям feature: сложный бизнес-сценарий, координация сущностей или потребность в самостоятельном переиспользуемом действии.

Дерево выбора состояния также допускает локальный `model/`: серверное состояние хранится в TanStack Query независимо от расположения hook; клиентское состояние может оставаться локальным для страницы. Разделяемое состояние внутри одной страницы не требует автоматически создавать entity или глобальный store.

## 2. Локальные и общие mock fixtures

По умолчанию mock-данные определяются в начале story-файла. Story-файлы не импортируют данные друг из друга.

Здесь также действует Local First: данные сначала хранятся локально. Разрешённое исключение: несколько stories одного модуля могут импортировать общие fixtures из `modules/{module}/shared/_mocks/`, когда им нужен один согласованный сценарий и совместное обновление данных полезно. Простого совпадения формы объекта или нескольких полей недостаточно для выделения общего fixture.

Например, имя пользователя для двух независимых карточек можно дублировать. Согласованный набор «сессия → assessment → участники», используемый несколькими компонентами одного сценария, можно вынести в общие fixtures.

В общей папке находятся обычные объекты данных. MSW handlers остаются в story-файлах, чтобы ответы, создающие конкретное состояние компонента, были видны в самой story.

Таким образом, требование дублировать mock-данные не является абсолютным. Раздел «Module-level shared handlers» следует понимать как «Module-level shared mock data»: сами handlers не выносятся.

## 3. Проверка mock-данных по схеме должна быть явной

Генерация `main-api-schema.ts` сама по себе не связывает произвольные объекты и `HttpResponse.json()` с контрактом endpoint.

Каждый mock-ответ явно проверяется через `satisfies` по типу ответа endpoint, полученному из сгенерированной схемы. Проверяется полный ответ, включая wrapper, а не только вложенная сущность. Story-файлы должны входить в проверку TypeScript.

```ts
import type { paths } from "@/shared/api/main-api-schema";

type ActiveSessionResponse =
  paths["/api/v1/session/active"]["get"]["responses"][200]
    ["content"]["application/json"];

const emptySessionResponse = {
  session: null,
} satisfies ActiveSessionResponse;
```

Путь к типу нужно сверять с реальной сгенерированной схемой. Такой подход обнаруживает несовместимые изменения формы данных при условии, что story-файлы включены в проверку TypeScript. Он не гарантирует обнаружение любого изменения API или семантической ошибки в данных.

## 4. Примеры stories должны соблюдать собственные правила

В основном примере `stories.md` следует мысленно применять исправления из раздела pitfalls:

- Для текущего пользователя использовать `/api/v1/user/me`, а не `/api/v1/developers/me`.
- Для активной сессии возвращать `{ session: mockSession }`, а для пустого ответа — `{ session: null }`.
- В Loading story задерживать фактический endpoint, от которого зависит загрузка компонента.
- Импортировать `delay` из `msw`, если используется `delay("infinite")`.
- Обрабатывать все остальные запросы, которые запускаются безусловно, в том числе в Loading story.

Имена endpoint и response shapes окончательно определяются исходниками hooks и сгенерированной схемой. Иллюстративный пример не имеет приоритета над ними.

## 5. Единая структура файлов компонента и stories

Используется соглашение из архитектуры: папка в `kebab-case`, компонент в `index.tsx`, имя экспорта в `PascalCase`. Story находится рядом:

```text
ui/
└── assessment-info-card/
    ├── index.tsx
    └── AssessmentInfoCard.stories.tsx
```

```ts
// AssessmentInfoCard.stories.tsx
import { AssessmentInfoCard } from "./index";
```

Пример с `_ui/AssessmentInfoCard.tsx` в `stories.md` показывает идею совместного размещения, но не задаёт альтернативное соглашение о папках и файлах.

## 6. Условия выделения widgets

Для widget достаточно самостоятельной сложной композиции нескольких entities/features. Повторное использование усиливает аргумент в пользу выделения, но не является обязательным условием.

Само наличие нескольких компонентов не требует выделения widget: обычные части страницы остаются в её `ui/components/`.

Упоминание «5+ places» считается примером очевидного повторного использования, а не минимальным порогом. Формулировка «and recurs» в сводной таблице не добавляет обязательного условия.

Для композиции разных модулей действует отдельное правило границ: она размещается в `src/widgets/`, даже если используется на одной странице. Это позволяет соблюдать запрет прямых импортов между модулями.

## 7. Владение доменом и глобальный shared

Использование доменного кода в нескольких частях приложения не отменяет принадлежность исходному модулю. Правило «used by 2+ modules → shared» применяется к общим примитивам, утилитам и инфраструктуре, а не автоматически ко всем entities и features.

Например, баланс остаётся в `payments`, профиль пользователя — в `auth`. Dashboard собирает их в `src/widgets/dashboard/`; переносить обе сущности в глобальный `shared/` не требуется.

Если сценарий одного модуля требует данные или действия другого, взаимодействие организуется на верхнем уровне композиции с передачей props/callbacks. Прямые импорты между модулями остаются запрещёнными.

Модульный `shared/` и глобальный `src/shared/` имеют разную область действия: первый обслуживает slices одного модуля, второй содержит действительно общие примитивы приложения.
